# Guardian browser extension

Manifest V3 extension, one codebase for Chrome and Edge. It reports the **registrable domain**
(eTLD+1), full host, page title and active seconds of the tab you are looking at to the Guardian
service on this computer (`POST http://127.0.0.1:47130/tab`). Path and query are never sent. It
makes no other network requests. The popup shows the child exactly what was sent in the last hour.

## Build

Requires Node 22.

```
cd extension
npm install
npm run build      # -> build/  (background.js, popup.js, popup.html, popup.css, manifest.json, icons/)
npm run typecheck  # tsc --noEmit
npm test           # node --test over src/*.test.ts (bundled with esbuild first)
```

Icons are generated by `scripts/make-icons.mjs` (plain Node + zlib, no native deps) into `icons/`
during `npm run build`.

### Layout

| File | Purpose |
| --- | --- |
| `manifest.json` | MV3 manifest: `tabs`, `idle`, `storage`, `alarms`; host permission for `http://127.0.0.1:47130/*` only |
| `src/tracker.ts` | Pure interval tracker + `registrableDomain()` (public suffix list via `psl`); unit tested |
| `src/background.ts` | Service worker: tab/window/idle events, 30 s heartbeat alarm, POST with 2 s timeout, retry queue (max 200), rolling one-hour `sentLog` |
| `src/popup.ts`, `popup.html`, `popup.css` | Popup: what is sent, last hour of reports, service status, "See my activity" link |
| `scripts/build.mjs` | esbuild bundle (IIFE, minified, `chrome110`) and static copy |
| `scripts/make-icons.mjs` | Writes the shield PNGs |

### How tracking works

- `tabs.onActivated`, `tabs.onUpdated` (URL/title change on the active tab), `windows.onFocusChanged`
  and `idle.onStateChanged` close the current interval and open a new one for the tab now in front.
  Losing window focus, idle and lock close the interval without opening a new one.
- A `chrome.alarms` heartbeat every 30 s flushes the open interval (report the elapsed part, restart
  at now), so the service never sees an interval longer than 30 s and a crash loses at most 30 s.
- Intervals under one second are dropped.
- `chrome://`, `edge://`, `about:`, `file:` and `localhost` URLs are never reported. IP addresses are
  reported as-is.
- Failed POSTs are queued in `chrome.storage.session` (up to 200) and retried on the next heartbeat.
- `browser` is `"edge"` when the user agent contains `Edg/`, otherwise `"chrome"`.

## Extension ID and packing

`manifest.json` deliberately has **no `key` field**. The Guardian service packs `build/` into a CRX
with a stable private key it owns; the extension ID is derived from that key, so it is the same on
every install and in every update. That ID is what the forcelist policy and `update.xml` refer to.
The `update_url` in the manifest is informational for packed builds; the forcelist entry below is
what actually tells the browser where to fetch updates from.

## Install on a managed PC (forcelist + update.xml)

The MSI writes these policy keys (HKLM) for both browsers:

```
HKLM\SOFTWARE\Policies\Google\Chrome\ExtensionInstallForcelist
  1 = <extension-id>;http://127.0.0.1:47130/ext/update.xml
HKLM\SOFTWARE\Policies\Microsoft\Edge\ExtensionInstallForcelist
  1 = <extension-id>;http://127.0.0.1:47130/ext/update.xml
```

`update.xml` is the standard Omaha update manifest served by the service:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<gupdate xmlns="http://www.google.com/update2/response" protocol="2.0">
  <app appid="<extension-id>">
    <updatecheck codebase="http://127.0.0.1:47130/ext/guardian.crx" version="1.0.0" />
  </app>
</gupdate>
```

The browser reads the forcelist, fetches `update.xml`, downloads the CRX from `codebase`, installs
it, pins it, and re-checks periodically; bumping `version` in the manifest and re-packing is all
an update needs. The extension cannot be disabled or removed by a standard user and the browser
shows the "managed by your organization" badge, which is the intended, overt signal.

### Why this does not work on an unmanaged home PC

Chrome and Edge only honor `ExtensionInstallForcelist` entries that point **off-store** (any
update URL other than the Web Store / Edge Add-ons store) when the machine is **managed**: joined
to an Active Directory domain, Microsoft Entra ID, or enrolled in MDM. On a plain home PC the
policy keys are read, but off-store entries are ignored as an anti-malware measure (the policy
page shows them as "blocked" or the extension simply never installs). Store-hosted extensions are
forcelisted fine on any machine, but Guardian is intentionally not published to a store.

Because of that, the Guardian tray program reads the **address bar of the foreground browser
window** (UI Automation) as a fallback and reports the same `{domain, title, activeSeconds}` with
`browser: "tray"`. It is coarser (no per-tab idle handling, title from the window caption) but keeps
web history working without the extension. The service raises an `extension_missing` alert when
the browser is in use and no extension reports arrive.

## Load unpacked for testing

1. `npm run build`
2. Open `chrome://extensions` (or `edge://extensions`).
3. Turn on **Developer mode**.
4. **Load unpacked** and pick `extension/build`.
5. Browse a few sites; click the Guardian toolbar icon to see what was sent. With the Guardian
   service running on `127.0.0.1:47130` the status reads "connected"; without it, reports queue.

Note that an unpacked load gets a different extension ID than the packed CRX (the ID comes from the
path instead of the key), so a forcelist entry will not match it. That only matters for the policy
install, not for testing.
